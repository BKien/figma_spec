## Retained Source Semantics

Registration name and password restrictions, email uniqueness and bcrypt cost 10 are retained. Account numbers use 8–34 digit characters, retaining leading zeros. Account list sorts by ID ascending; detail includes the five most recent transactions with signed amounts. Account deletion includes its transactions. Bills include today through day +30, exclude already charged due cycles and sort by due date, amount descending, then ID. Goal dates are prospective, inclusive for overlap detection and bounded to 366 calendar days; expense goals require a category and saving goals prohibit one. Saving progress can be negative. Expense-goal priority is reached/exceeded first, then end date, target and ID. Savings comparisons include every month of target year and prior year.

## Transaction Boundaries

Account create is protected by the unique (user_id, number_fingerprint) constraint. Transaction create locks the chosen account, checks the supplied version and completed-expense funds, inserts exactly one row, changes balance only for Complete, increments account version and commits. Account update locks and checks the account, replaces the requested fields, adds a correction row if needed and commits. Delete locks and checks version, deletes children and the account in one transaction. Goal create locks the user before conflict checking and insertion. Goal target update compares version while writing; it does not change goal type/category/date interval.

No idempotency store is specified. After a network outcome that does not establish whether the operation committed, the client reloads the relevant list/detail before offering a new submission. An unchanged old resource version receives a conflict after a successful mutation. This does not promise semantic deduplication across new attempts with new versions.

## Compatibility and Evidence Limits

Envelope changes, added expected_version/If-Match and version fields, stricter year/path parsing, category/transaction identity fields, Complete-only cash-flow accounting, protected account-number storage and memory-only sessions require coordinated implementation changes if a backend already follows the spreadsheet. This task creates specifications only. The source does not provide implementation code, a Figma file, screenshots, a database or application behavior for verification. Raw source claims about AGENTS.md and PROJECT_CONTEXT.md refer to other work and are not instructions for this repository.
